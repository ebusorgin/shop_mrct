# Единая сущность техкарт и полуфабрикатов на карте производства

Дата: 2026-11-18
Статус: согласовано, готово к планированию реализации

## Задача

Полностью переделать логику техкарт и полуфабрикатов: объединить их в одну
сущность, импортировать текущие позиции и отобразить всё на карте производства.

## Принятые решения

1. **Источник истины — узел карты** (`prod_nodes`) вместе с его операцией
   (`prod_ops`). `state` (заготовка) и `output` (блюдо) — только роль на карте;
   редактирование состава, потерь, фасовок, цен и каталога одинаковое.
2. **Заказы магазинов, отчёты-отгрузки и списание по доставке сразу переходят
   на карту** (`prod_packagings` / `prod_nodes`).
3. **Текущий граф карты заменяется импортом** (25 демо-узлов и 9 операций
   удаляются; совпадающие позиции восстанавливаются из старых данных).
4. **Техкарты-фасовки сворачиваются** в фасовки узла полуфабриката.
5. **Старые числа сохраняются**: партия остаётся равной старому `out_qty` /
   `portion_qty`, проверка «сумма нетто = партия» становится предупреждением.
6. **Интерфейс: карта + список рецептур** в боковой панели; старые страницы
   «Полуфабрикаты» и «Техкарты» удаляются.

## Целевая модель данных

- `prod_nodes` — сырьё (`product`, ссылка на `products`), заготовки (`state`),
  блюда (`output`). Узел несёт названия (name/name_en/name_sr), единицу,
  порцию, каталог, цену, заметку.
- `prod_ops` — ровно одна операция-производитель на узел: состав
  (`prod_op_inputs`), потери на связи, партия (`plan_qty`/`plan_unit_id`),
  человекочасы.
- `prod_packagings` — фасовки узла: вес, цена, база цены, себестоимость,
  минимальный заказ, доступность магазинам.
- Новые колонки трассировки:
  - `prod_nodes.legacy_kind` (`semi` | `card` | null), `prod_nodes.legacy_id`;
  - `prod_ops.legacy_source` (`semi` | `card` | null), `prod_ops.legacy_id`;
  - `prod_packagings.legacy_id` (id из `product_packagings`);
  - `prod_packagings.title`, `title_en`, `title_sr` — исходные названия свёрнутой
    техкарты для печати и витрины (переводы вариантов фасовок не теряются).
- `store_order_items.packaging_id` переключается на `prod_packagings(id)`.
- Таблицы `tech_cards`, `tech_card_items`, `semi_products`, `semi_inputs`,
  `product_packagings` остаются read-only архивом; новый код их не читает.
  Удаление — отдельным решением после стабилизации.

## Импорт

Одноразовый идемпотентный скрипт в одной транзакции, маркер в
`app_migrations` (`legacy_to_map_v1`). Отчёт: созданные узлы/операции/связи/
фасовки, несбалансированные операции, несопоставленные позиции.

Правила:

1. Каждое сырьё из составов → один `product`-узел (dedupe по `products.id`).
2. Каждый полуфабрикат → `state`-узел + операция:
   - партия = `semi_products.out_qty`, единица выхода = `unit_id`;
   - входы = `semi_inputs` как есть (qty → qty, `yield_pct` → `loss_pct = 100 − yield`);
   - вложенный полуфабрикат → связь на его узел;
   - `portion_qty` узла = `out_qty` (справочно).
3. Техкарты:
   - **сворачиваемые (10)**: ровно одна строка `semi`, название совпадает с
     полуфабрикатом либо это вариант фасовки. Новый узел не создаётся;
     фасовки, цены, доступность и `title` (исходное имя техкарты) переезжают
     на узел полуфабриката; каталог узла — из техкарты;
   - **остальные (44)**: `output`-узел + операция, партия = `portion_qty`;
     входы `raw`/`semi`/`product` (product → узел соответствующей техкарты);
     фасовки копируются 1:1.
4. Координаты узлов и операций = 0; клиентская авто-раскладка разложит граф
   слоями при первом открытии. Версия карты инкрементируется.
5. Заказы: таблица соответствия `old packaging id → new prod_packaging id`;
   обновляются `store_order_items` (13 930 строк) и массивы
   `store_orders.line_order` (8 заказов). Номера заказов не меняются.
6. Перед применением на проде — `pg_dump`; на локальной копии миграция
   прогоняется и проверяется.

Ожидаемый объём: 26 state-узлов, 44 output-узла, ~70 операций, ~363 связи,
62 фасовки (36 доступных), около 60 product-узлов.

## Стабильные идентификаторы и архив (обязательное следствие перевода заказов)

После перехода заказов на `prod_packagings` сохранение карты больше не может делать
`delete` + `insert`: история заказов держит FK на фасовки. Поэтому:

- добавляем `prod_nodes.archived` и `prod_packagings.archived` (boolean, default false);
- `PUT /api/production-map` становится upsert по `uid` (= id из БД): существующие узлы,
  операции и фасовки обновляются, новые вставляются;
- позиции, которых нет в присланной карте, не удаляются, а помечаются `archived`;
  GET карты скрывает архив, отчёты, история и раскрытие состава архив видят;
- операции архивных узлов сохраняются, чтобы старые заказы продолжали раскрываться;
- удаление узла в интерфейсе = архивирование; каталог магазина показывает только
  `archived = false AND available`;
- клиент передаёт `uid` фасовок при сохранении, сервер сохраняет их id.

`prod_packagings` с `available = true` обязаны иметь цену; каталог обязателен, только
если у узла есть хотя бы одна доступная фасовка. Недоступные фасовки без каталога и
цены (26 старых позиций) сохраняются как есть.

## Проверка баланса

`PUT /api/production-map` больше не отвечает 400 при расхождении партии и
суммы нетто. Ответ содержит `warnings: [{ opUid, plan, net, diff }]`;
сохранение проходит. В карточке операции — бейдж «партия ≠ сумма нетто».
Остальные проверки (ссылки, циклы, один производитель, единицы, каталог и
цены при наличии фасовок) остаются блокирующими.

## Backend

- Удаляются роутеры `/api/semis`, `/api/cards`, `/api/batches` и связанный код.
- Каталог магазина, проверка доступности, сохранение заказа — `prod_packagings`.
- Отчёт-отгрузка, архив, история, статистика магазинов — `prod_nodes` +
  `prod_packagings`; `line_order` хранит id фасовок карты; название строки —
  `node.name` либо `packaging.title` для свёрнутых техкарт.
- Списание по доставке раскрывает заказы по графу карты: количество в единице
  узла = `qty × qty_base`; масштаб операции = требуемое / `plan_qty`; потери —
  как на связях. Результат должен совпасть со старым `expandCard`.
- Google Sheets: чтение/запись цен и строк заказов через фасовки карты;
  сопоставление по `legacy_id` и имени узла.
- Панель (последние партии), «где используется сырьё», счётчики каталогов,
  проверка уникальности имён (`prod_nodes`), ИИ-подсказки коэффициентов —
  переводятся на карту; ветка полуфабрикатов в ИИ удаляется.
- `seed.ts` для чистых баз создаёт карту, а не старые таблицы.

## UI

- Меню: один пункт «Карта производства»; «Полуфабрикаты» и «Техкарты»
  убираются, старые URL редиректят на `/map`.
- Боковая панель карты: вкладки «Сырьё» и «Рецептуры». Во второй — поиск,
  бейдж роли (заготовка/блюдо), число фасовок, предупреждение о дисбалансе;
  клик выбирает узел.
- Панель узла: названия, единица, порция, каталог, фасовки (цена,
  себестоимость, база, доступность, минимальный заказ), состав и потери через
  операцию; выпуск партии и отгрузка без изменений.
- Магазинная часть визуально не меняется (те же 36 доступных фасовок).

## Миграция и выкат

- Скрипт `server/scripts/migrate-legacy-to-map.ts`,
  `npm run migrate:map -- --dry-run|--apply`; идемпотентный, транзакционный,
  пишет отчёт и маркер.
- Автозапуск на старте не делаем. Если маркер отсутствует, новые эндпоинты
  отвечают 503 «Требуется миграция данных на карту производства».
- Локально: бэкап → `--apply` → проверки. Прод — только после отдельного
  подтверждения пользователя.

## Критерии приёмки

1. Все 26 полуфабрикатов и 54 техкарты представлены на карте (10 свёрнуты в
   фасовки).
2. Для каждой старой техкарты и фасовки потребность в сырье совпадает со
   старым расчётом с точностью до 0,001.
3. Отчёт-отгрузка за прошлые даты совпадает по строкам, количеству, весу,
   нетто, PDV и сумме; 13 930 строк заказов и 8 `line_order` открываются.
4. Каталог магазина показывает те же 36 доступных фасовок; цены и
   себестоимость совпадают.
5. Списание по доставке даёт тот же расход сырья.
6. Офис и магазин видят только свои данные; магазин не видит себестоимость.
7. Сохранение карты с дисбалансом проходит и показывает предупреждение;
   выпуск партии и отгрузка работают на импортированных узлах.
8. `npm run build` сервера и клиента, тесты сервера, браузерная проверка под
   офисной и магазинной ролью.
