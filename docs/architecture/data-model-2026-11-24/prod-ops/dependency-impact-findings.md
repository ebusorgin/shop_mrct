# Нужна ли таблица `prod_ops`

**Дата:** 2026-11-24  
**Вопрос:** можно ли удалить или слить `prod_ops`  
**Гранулярность:** таблица → сервисы → API → UI → бизнес-процессы  
**Источник:** текущий код `main`, локальная копия прод-базы от 2026-11-23

## Короткий ответ

**Да, в текущей архитектуре `prod_ops` нужна.** Она владеет составом операции (`prod_op_inputs.op_id`), связывает операцию с результатом (`output_node_id`) и используется выпуском партии, списанием по доставке, API карты и редактором рецептур.

Но как **отдельная сущность** она сейчас избыточна: в данных ровно **109 операций на 109 не-сырьевых узлов**, без сирот, без узлов без операции и без нескольких операций на один результат. Это фактически 1:1-расширение `prod_nodes`. Удалять её «просто так» нельзя, а слияние — отдельный рефакторинг с миграцией.

## Что показывают данные

| Проверка | Результат |
|---|---|
| `prod_ops` | 109 |
| Активные не-сырьевые `prod_nodes` (`state` + `output`) | 109 |
| Узлы без операции | 0 |
| Операции с несуществующим/сырьевым выходом | 0 |
| Несколько операций на один выход | 0 |
| `prod_op_inputs` | 549 (от 1 до 17 входов на операцию, в среднем 5) |
| `plan_qty` = `prod_nodes.portion_qty` | 109 из 109 |
| `plan_unit_id` = `prod_nodes.unit_id` | 109 из 109 |
| `labor_hours > 0` | 0 |
| `yield_pct` заполнен | 0 |
| `note` заполнен | 38 |
| `x/y` заданы | 0 |
| `map_batches` | 0; связи по `op_id` нет, только `op_name` |

Имя операции и имя узла не совпадают: например, операция `производство` производит узел `картофель варённый`. То есть `prod_ops` — не буквальный дубль строки `prod_nodes`, но её полезная нагрузка в текущих данных сводится к имени операции и владению составом.

## Что зависит от `prod_ops`

| Зависимость | Характер | Последствие удаления |
|---|---|---|
| `prod_op_inputs.op_id` (549 строк) | Прямая, без FK | Состав теряет владельца; нужно переименовать в `prod_node_inputs` и перепривязать к `node_id` |
| `prod_nodes.output_node_id` (109) | Обратная ссылка | Нельзя понять, какая операция производит узел |
| `map-production.ts` | `loadGraph`, `outputQty`, `expand`, `produceMapBatch`, `expandNodeNeedTx` | Ломаются выпуск партии, отгрузка и списание по доставке |
| `map-save.ts` | Upsert операций и входов | Сохранение карты перестаёт сохранять состав |
| `production-map.ts` | GET/PUT `/api/production-map`, `POST /ops/:id/produce` | Ломается API редактора карты |
| UI карты | 124 упоминания `op` в `production-map.component.ts`, модели API и расчёт | Ломается визуальный редактор и блоки операций |
| UI рецептур | 2 упоминания в `recipes.component.ts` | Ломаются переходы/связи с операцией |
| `products/:id/usage` | `join prod_ops o on o.id = i.op_id` | Нельзя показать, где используется сырьё |
| `seed.ts` | Демо-операции | Демо-данные неполные |
| `map_batches` | Только `op_name`, без `op_id` | История уже не связана ключом; удаление `prod_ops` не улучшит, а ухудшит ситуацию |

Итого: **54 упоминания в 6 серверных файлах и 132 упоминания в 4 клиентских файлах**. Это не «мёртвая» таблица.

## Варианты

### 1. Оставить сейчас — рекомендуемый

Риск минимальный, пользовательской выгоды от удаления нет. Если хочется навести порядок в схеме:

- добавить `unique (output_node_id)` и, желательно, FK `output_node_id → prod_nodes(id)`, чтобы 1:1 было гарантировано БД, а не только `validateShape`;
- убрать `yield_pct`, если он не будет реализован в формуле (сейчас он всегда null и в расчёте не участвует);
- не дублировать `plan_qty`/`plan_unit_id`, если план всегда равен `node.portion_qty`/`node.unit_id`; либо явно оставить их как «план партии», если планируется расхождение с выходом узла;
- при следующем изменении истории добавить `op_id`/`node_id` в `map_batches`, иначе выпуски остаются привязанными только к именам.

### 2. Слить в `prod_nodes` — отдельный рефакторинг

Если цель — упростить модель, можно хранить операцию как поля узла (`op_name`, при необходимости `labor_hours`, `yield_pct`), а `prod_op_inputs` переименовать в `prod_node_inputs` с `node_id`. Это затрагивает:

- миграцию 109 операций и 549 входов;
- API карты и сохранение;
- выпуск, отгрузку, списание по доставке;
- UI карты и рецептур;
- seed.

Пользовательской выгоды сейчас нет, риск высокий. Делать это стоит только вместе с переработкой карты, а не как «убрать лишнюю таблицу».

### 3. Просто удалить — нельзя

Потеряется состав рецептур, перестанут работать выпуск и списание, сломаются API и UI. Без предварительной миграции данных это недопустимо.

## Рекомендация

**Оставить `prod_ops`.** Считать её не «лишней таблицей», а текущим владельцем состава операции. Навести порядок можно без удаления: закрепить 1:1 уникальным индексом/FK, убрать неиспользуемый `yield_pct` и решить, нужны ли отдельные `plan_qty`/`plan_unit_id` при их полном совпадении с узлом.

## Что проверить перед решением

1. Подтвердить на production те же 109/109 и отсутствие операций с архивными/сырьевыми выходами.
2. Проверить, планируется ли несколько операций на один результат; сейчас модель это запрещает.
3. Проверить, нужен ли `yield_pct` в бизнес-расчёте; если нет — удалить поле, а не таблицу.
4. Проверить, нужен ли отдельный план партии, отличный от `portion_qty`; если нет — не дублировать.
5. Для истории выпусков решить, добавлять ли `op_id`/`node_id` в `map_batches`.
