# Архитектурное ревью: MIX markt CRM и бизнес-модель

**Дата:** 2026-11-24  
**Репозиторий:** `A:\projects\shop_mrct`, ветка `main` (a4fddd6 + локальные незакоммиченные файлы)  
**Статус:** read-only ревью, production не запрашивался и не изменялся

## 1. Коротко

Ядро системы — склад, накладные, карта рецептур, заказы магазинов и Otpremnica — в целом следует задокументированным правилам. Но есть три критичных расхождения, которые могут испортить живые данные:

1. **Удаление сырья ломает живые рецептуры.** Проверка ссылок смотрит только на старые таблицы `tech_cards`/`semi_products`, а не на действующую карту `prod_nodes`/`prod_op_inputs`. Сейчас 46 из 112 видов сырья, используемых в карте, можно физически удалить.
2. **Откат накладной может исказить склад и среднюю себестоимость.** Количество при откате пересчитывается по текущим коэффициентам товара, а не по снимку движения; пересчёт `avg_cost` по журналу учитывает возвраты партий карты с `unit_cost = 0`.
3. **Склад неполный: 97 из 118 продуктов не имеют строки `stock`.** Они не видны на странице склада и не попадают в алерты низкого остатка, пока по ним не пройдёт первое движение.

Отдельно: бизнес-модель в скилле `mix-markt-business-logic` (v0.2.0) устарела в части полуфабрикатов/техкарт, цен Otpremnica и ставки PDV. А целевая розничная модель из roadmap (локации, остатки магазинов, приёмка, продажи, финансы) в `main` ещё не начата; частично она существует только в долгой ветке `local/stock-lots-20261120`.

## 2. Базы сравнения и метод

Сравнение велось с двумя разными «бизнес-моделями», их нельзя смешивать:

- **Модель A — правила учёта** из скилла `mix-markt-business-logic` v0.2.0: единицы, склад, накладные, рецептуры, заказы, роли, аудит.
- **Модель B — целевая розничная операционная модель** из `docs/superpowers/specs/2026-11-17-retail-operations-roadmap.md`: единый контур «заказ → производство → отгрузка → приёмка → остаток магазина → продажа → финансы».

Источники доказательств:

- код `server/src`, схема `server/sql/init.sql`;
- локальная копия прод-базы от 2026-11-23 (118 продуктов, 1022 заказа, 4 движения);
- тесты `server/test` (11 тестов, все проходят);
- git-ветки и история.

Ограничения: production не проверялся, UI-сценарии под ролями не прогонялись, сборка не перепроверялась. Данные ниже — состояние локальной копии, а не текущий production.

## 4. Критичные расхождения

### BM-01. Удаление сырья, используемого в живой карте

**Правило.** Физическое удаление продукта допустимо только при нулевом остатке и отсутствии ссылок; иначе — архив (`mix-markt-business-logic`, §2).

**Факт.** `productsRouter.delete` проверяет только `semi_inputs` и `tech_card_items`:

- `server/src/routes/products.ts:314-320` — запрос ссылок;
- `server/src/routes/products.ts:348-359` — физическое удаление и очистка истории.

Действующая карта хранит ссылки в `prod_nodes.ref_id` и `prod_op_inputs.node_id`, но внешних ключей на `products` нет (`server/sql/init.sql:935-946`, `972-983`). Поэтому удаление проходит без ошибки.

**Данные.** Из 112 видов сырья, используемых в карте, 46 имеют нулевой остаток и не встречаются в старых таблицах — именно они сейчас «удаляемы». Ещё 60 защищены только историческими ссылками legacy-таблиц.

**Влияние.** После удаления раскрытие рецепта падает с «Продукт #… из техкарты не найден», ломаются выпуск партии, списание по доставке и предпросмотры. Восстановить продукт с тем же id нельзя.

**Что сделать.** Добавить проверку `prod_nodes`/`prod_op_inputs` (и `prod_packaging_tare`) в удаление, поставить FK или триггер, закрыть путь «архив вместо удаления» для всех ссылок карты. Плюс тест: попытка удалить сырьё из карты возвращает архив, а не удаление.

### BM-02. Откат накладной искажает количество и себестоимость

**Правило.** Откат — не удаление строк: списание прихода, статус `reversed`, затем пересчёт остатка и `avg_cost` по журналу с исключением всех отменённых накладных. Если товар израсходован, откат падает.

**Факт, часть 1 — количество.** `reverseWaybill` берёт строки накладной (`qty`, `unit_id`) и заново пересчитывает базовое количество через текущие коэффициенты товара:

- `server/src/routes/waybills.ts:358-372` — выборка и `toBaseCross`;
- `server/src/routes/waybills.ts:371-381` — списание.

Если после прихода менялась базовая единица, `g_per_pcs`, `ml_per_pcs` или `g_per_ml`, откат спишет не то количество, которое было принято. Правильный источник — движение прихода (`movements.qty`), а не пересчёт «на сегодня».

**Факт, часть 2 — себестоимость.** Пересчёт `avg_cost` идёт по всем движениям, кроме отменённых накладных:

- `server/src/routes/waybills.ts:393-413`.

При этом возврат партии карты создаётся как `receipt` без `unitCost`:

- `server/src/services/map-production.ts:318-328`;
- `server/src/services/stock.ts:69` — для такого прихода в журнал пишется `unit_cost = 0`.

При следующем откате накладной этот возврат участвует в пересчёте как приход по нулевой цене и тянет среднюю вниз. Сейчас отменённых партий и накладных в локальной копии нет, то есть дефект латентный, но он сработает на первом же реальном сторно.

**Влияние.** `stock.qty` перестаёт соответствовать журналу; средняя себестоимость «отравляется»; дальше страдают отчёты по себестоимости и списания по средней.

**Что сделать.** Хранить базовое количество в `waybill_items` на момент прихода (или восстанавливать из `movements`), а при пересчёте `avg_cost` учитывать происхождение прихода: возврат без переоценки не должен попадать в среднюю как нулевой приход. Нужны тесты: изменение коэффициента после прихода; откат накладной после отмены партии карты.

### BM-03. Неполный склад: 97 продуктов без строки `stock`

**Правило.** При создании продукта всегда создаётся строка `stock` с нулём; остаток и низкий остаток считаются по `stock` (`mix-markt-business-logic`, §2-3).

**Факт.** В локальной копии 118 активных продуктов и только 21 строка `stock`. Строки есть у 15 старых демо-позиций и 6 позиций упаковки; остальные 97 продуктов (в основном из PDF-merge и миграции карты) строки не имеют. Приложение заводит строку только при первом движении (`server/src/services/stock.ts:34-43`), но бэкфилла в `init.sql` нет.

Страница склада делает внутренний join:

- `server/src/routes/stock.ts:17-21` — `from stock s join products p`.

**Влияние.** 97 позиций не видны в «Складе», не участвуют в алертах «ниже минимума» и в KPI стоимости склада, пока по ним не пройдёт приход или корректировка. Это противоречит самой идее «склад — единая точка правды».

**Что сделать.** Идемпотентный бэкфилл `insert into stock … select …` при старте (или одноразовая миграция в `app_migrations`), а список склада перевести на `left join`, чтобы отсутствие строки было видно как 0, а не как пропажа товара.

## 5. Средние расхождения

### BM-04. Пустая операция может быть выпущена

`parseBody` разрешает сохранить операцию без входов как черновик (`server/src/routes/production-map.ts:400-401`). Если у такой операции задан `plan_qty`, `outputQty` вернёт план (`server/src/services/map-production.ts:89-98`), `expand` не найдёт входов (`128-140`), и `produceMapBatch` создаст партию с нулевой себестоимостью и без списаний (`189-205`). Правило «пустая техкарта не проводится» не выполнено. Сейчас таких операций в данных 0, но API это позволяет.

### BM-05. Дубли фасовок по выходу

Сервер не проверяет уникальность `qty_base` в пределах узла: `server/src/routes/production-map.ts:100-137` и `server/src/services/map-save.ts:116-158`. В данных уже есть живой пример: «Квашеная капуста» с двумя фасовками по 1000 г (одна недоступна, одна доступна). Правило «выходы уникальны в пределах техкарты» нарушено. Старый путь (`server/src/services/packagings.ts:60-69`) такую проверку делал, новый — нет.

### BM-06. `min_order` не проверяется на сервере

Клиент магазина не даёт уйти ниже минимума (`client/src/app/orders/store-orders.component.ts:283-290`), но `PUT /api/store/orders/current` принимает любое целое 1…999 (`server/src/routes/store.ts:107-127`, `200-206`). В данных 11 строк ниже `min_order`. Если минимум подняли после сохранения — это нормальная история, но API позволяет обойти правило и сейчас.

### BM-07. `yield_pct` операции — мёртвый показатель

Поле хранится (`server/sql/init.sql:954-964`), отображается как «выход X %» (`client/src/app/pages/production-map.component.ts:2075-2078`, `2173-2176`), но ни серверное раскрытие, ни клиентский расчёт его не используют: считаются только `loss_pct` на связях (`server/src/services/map-production.ts:128-140`, `client/src/app/core/production-map-calc.ts:152-198`). Сейчас все `yield_pct` в базе `null`, поэтому вреда нет, но пользователь может выставить 80 % и не увидеть никакого эффекта. Нужно либо убрать поле из UI, либо реализовать его в формуле и синхронизировать сервер/клиент.

### BM-08. Роли рецептур и каталог — только в клиенте

Сервер требует цену для доступной фасовки и каталог при наличии доступной фасовки (`server/src/routes/production-map.ts:137-145`), но не реализует правило «блюдо — это рецепт с фасовкой; убрали последнюю — снова заготовка и каталог „заготовки“». Это остаётся на клиенте. Любой другой потребитель API может сохранить состояние, которое UI считает невозможным.

### BM-09. Заказ фасовки архивного узла

Каталог заказа исключает архивные узлы (`server/src/routes/store.ts:64`), а сохранение заказа проверяет только саму фасовку (`server/src/routes/store.ts:200-206`, `224-227`). Через API можно заказать доступную фасовку узла, который уже в архиве. Это расхождение между витриной и записью.

### BM-10. Аудит карты без diff

Сохранение карты пишет только количество узлов/операций и число предупреждений (`server/src/routes/production-map.ts:461-466`). Изменения цен, себестоимости, состава и потерь по журналу не восстановить. Для продукта diff есть (`products.ts:279-292`), для карты — нет. Учитывая, что карта определяет себестоимость, это существенный пробел аудита.

### BM-11. Списание по доставке считает до блокировки

`deliveryWriteoffPreview`/`postDeliveryWriteoff` сначала строят потребность и цены (`server/src/services/delivery-writeoff.ts:247-265`, `292-314`), и только потом блокируют строки склада (`324`). Между расчётом и блокировкой средняя может измениться; в движение уйдёт `unit_cost` из предпросмотра, а `cost_total` будет посчитан по нему же. Нужно блокировать склад до расчёта стоимости/дефицита или перечитывать `avg_cost` после блокировки.

### BM-12. Нумерация при сохранении и порядок печати

`ensureDeliveryDocNumbers` нумерует заказы даты в порядке печати (код магазина, id) и это покрыто тестами. Но `assignOrderDocNumber` при сохранении заказа выдаёт номер сразу (`server/src/routes/store.ts:233`, `server/src/services/order-numbering.ts:27-36`), в порядке сохранений. Если заказ создан вручную после импорта, его номер может оказаться выше, чем у магазина с меньшим кодом, и печатный порядок снова нарушится. Для сценария «импорт → печать» риск низкий, но остаточный.

### BM-13. Дрейф FIFO-ветки

В `main` склад по-прежнему средневзвешенный, без партий и сроков годности. В ветке `local/stock-lots-20261120` — 3 коммита и +1502/−161 строки: `stock_lots`, `movement_lots`, FIFO, срок годности, изменения в `stock.ts`, `waybills.ts`, `map-production.ts`, `delivery-writeoff.ts` и UI. Это не «мелкая недоделка», а альтернативная модель склада. Пока ветка не слита, бизнес-модель «партии и FEFO» в системе отсутствует, а при слиянии будет конфликт с любыми правками склада в `main`.

### BM-14. PDV в Otpremnica регулируется от 0 до 100 %

Правило в скилле: PDV 20 %. В API ставка стала параметром отчёта (`server/src/routes/orders.ts:52-58`), по умолчанию 20 %, но можно сформировать печатный документ с 0 %, 10 % или любым другим значением (`server/src/services/order-report.ts:170`, `236-243`). Магазинный отчёт всегда 20 % (`server/src/routes/store.ts:176`). Для официального документа это риск: лучше ограничить допустимые ставки (10/20) или зафиксировать 20 % для Otpremnica, оставив произвольную ставку только для внутреннего предпросмотра.

### BM-15. Остатки старой модели в коде

`server/src/services/packagings.ts` всё ещё содержит `savePackagings`, `defaultPackaging`, `packagingsSql` и работает с `product_packagings`; из него используются только подписи (`packagingLabel`, `packagingWeight`). `init.sql` продолжает создавать `semi_products`, `tech_cards`, `product_packagings`. Часть проверок (удаление продукта, использование сырья) до сих пор смотрит в legacy-таблицы. Это корень BM-01 и источник будущих расхождений: два источника истины для одной предметной области.

## 6. Устаревшая бизнес-модель (документация vs код)

Это не ошибки кода, а расхождения модели, которые нужно зафиксировать, иначе следующая сессия снова будет проектировать по старым правилам.

| ID | Раздел модели | Что написано | Что в коде |
|---|---|---|---|
| DOC-01 | §5-6 | Полуфабрикаты и техкарты — живые сущности | С 2026-11-19 карта `prod_nodes`/`prod_ops` — источник истины; `tech_cards`/`semi_products` — read-only архив |
| DOC-02 | §7 | Otpremnica строится по текущим ценам, прошлые отчёты пересчитываются | Для прошедших дат строки фиксируются слепком (`order-price-snapshot.ts`), прошлые документы не пересчитываются |
| DOC-03 | §7 | PDV всегда 20 % | Офисный отчёт принимает `vat` 0…100 %; 20 % — только значение по умолчанию |
| DOC-04 | §9 | Каталог `server/test` отсутствует | Есть `test/legacy-map.pure.test.ts` и `test/order-numbering.pg.test.ts`, 11 тестов проходят |
| DOC-05 | §3 | Остаток всегда пересчитывается из журнала | Технически да, но в данных 21 строка склада и 4 движения; «нулевые» остатки не имеют входящих движений, поэтому проверить происхождение нельзя |

Рекомендация: выпустить `mix-markt-business-logic` v0.3 с разделами «карта производства», «слепки Otpremnica», «настраиваемый PDV», «партии/FIFO (ветка)» и явным списком legacy-таблиц. Для решений «слепок вместо текущей цены» и «настраиваемый PDV» нужен ADR: сейчас они выглядят как самовольное изменение модели.

## 7. Целевая розничная модель: карта разрывов

Сравнение с `2026-11-17-retail-operations-roadmap.md`. Это ожидаемые разрывы, а не баги; они показывают, насколько текущая система ещё «производственная», а не «сетевая».

| Модуль целевой модели | Статус в `main` | Доказательство |
|---|---|---|
| Локации и остатки магазинов | Нет | В `init.sql` нет `locations`, `store_stock`; склад один |
| Партии, сроки годности, FEFO | Нет в `main`, есть в ветке | `local/stock-lots-20261120`, +1502 строки |
| Выпуск создаёт готовую продукцию на склад | Нет | `produceMapBatch` только списывает сырьё, остаток готовой продукции не появляется |
| Отгрузка как документ, транзит, приёмка | Нет | Otpremnica — отчёт; `store_delivery_writeoffs` — списание сырья, не отгрузка |
| Приёмка магазином и расхождения | Нет | Нет таблиц приёмки, претензий, статусов поставки |
| Продажи магазина / Z-отчёт / POS | Нет | Нет таблиц продаж и списаний по продажам |
| Списания с причиной, фото, стоимостью | Частично | Есть ручное списание по доставке с заметкой; причин, фото и порогов нет |

| Планирование производства из заказов | Нет | Партии выпускаются вручную |
| Заказы поставщикам, договоры, кредиторка | Нет | Есть накладные и оцифрованные счета, заказов поставщикам нет |

Вывод: первый приоритет владельца («потери и остатки») в `main` не начат, кроме ручного списания по доставке. Если розничная модель остаётся целью, следующим крупным шагом должна быть фаза 0 roadmap (локации + партии), а не дальнейшее расширение производства.

## 8. Что можно доверять

Подтверждено кодом и/или данными:

- изоляция магазина: `storeId` всегда из сессии, `requireStore`/`requireOffice` на маршрутах;
- конфиденциальность себестоимости: магазинные отчёты и архив не содержат `cost`/`avg_cost`, режим `cost` доступен только офису;
- транзакционность прихода, выпуска, списания и сохранения заказа;
- уникальность номера действующей накладной (409, освобождение при `reversed`);
- разделение «Умного прихода»: `parse` не создаёт движений, проведение только в `confirmImport` → `ingestWaybill`;
- проверка циклов, дублей входов и единственного производителя при сохранении карты;
- ровно одна фасовка по умолчанию на узел (в данных 0 нарушений);
- нумерация Otpremnica: 11 тестов, включая параллельную печать, проходят;
- отсутствие отрицательных остатков и расхождений `stock.qty` с суммой движений по тем продуктам, где движения есть.

Не проверено: production-база, реальные роли в UI, сборка клиента/сервера после незакоммиченных изменений, e2e-сценарии приёмки/списания.
