# MIX markt CRM — система учёта продукции производства

Клиент‑серверное приложение: **Node.js (Express + TypeScript) · PostgreSQL · Angular 19**.

## Возможности (по ТЗ)

| Раздел | Что делает |
|---|---|
| 📥 **Входящие накладные** | Вносим позиции из накладной поставщика (продукт, кол-во в любой единице — кг/шт/л — цена). При проведение всё автоматически приходует на склад с пересчётом в складские единицы и средневзвешенную себестоимость. |
| 🏬 **Склад** | Остатки по позициям, себестоимость, стоимость склада; поиск/фильтр по категориям; алерт «ниже минимального остатка»; журнал всех движений с фильтрами; ручные корректировки (инвентаризация); CRUD номенклатуры. |
| 🔪 **Полуфабрикаты** | Конструктор заготовок с **уварком/очисткой в %**: «Картофель варёный» = Картофель, выход 90 % (из 10 кг → 9 кг). Можно добавлять компоненты-добавки (масло, уксус… на 1 ед. выхода) и видеть предпросмотр расхода сырья. |
| 📐 **Техкарты** | Состав готовой продукции **на порцию**: позиции — либо сырьё со склада, либо полуфабрикат. Автоматическая **блок-схема**: сырьё → полуфабрикат (с % уварка) → техкарта. Проверка расхода: сколько сырья уйдёт на N порций и хватает ли на складе. |
| 🚚 **Расход продукции** | Отгрузка: «20 порций борща 400 г» → система раскрывает техкарту через полуфабрикаты с учётом уварки/очистки, **списывает сырьё со склада**, фиксирует дату, себестоимость партии и снимок списанного. Партию можно отменить — сырьё возвращается на склад. |

Стартовая «Панель» — KPI: стоимость склада, отгрузки за день, завершающиеся позиции, последние накладные.

## Как запустить

### 1. База данных (Docker)
```powershell
docker compose up -d db
```
(без Docker: поставьте PostgreSQL 14+, создайте БД `mixmarkt_crm` и правьте `server/.env`)

### 2. Сервер (API, порт 4000)
```powershell
cd server
npm install
# .env уже создан из .env.example; при необходимости поправьте доступ к БД
npm run db:seed   # миграции + демо-данные (борщ из ТЗ, овощи, уварки)
npm run dev       # или npm run build && npm start (прод)
```
API: `http://localhost:4000/api/health`

### 3. Клиент (Angular, порт 4200)
```powershell
cd client
npm install
npm start         # ng serve + прокси /api -> :4000
```
Открыть: **http://localhost:4200**

### 4. Автозапуск (прод на рабочей машине)
Сервер раздаёт и API, и собранный клиент одним процессом, поэтому для боевой машины достаточно: собрать и поставить задачу на вход в Windows.

```powershell
npm run build                 # server + client в dist
npm run autostart:install     # задача Планировщика MixmarktCRM-Autostart
npm run autostart:run         # то же самое, но вручную (для проверки)
npm run autostart:remove      # убрать автозапуск
```

При входе в систему `scripts/start-crm.ps1` ждёт Docker Desktop, поднимает `mixmarkt-crm-db`,
старует `pm2 startOrReload ecosystem.config.js`, делает `pm2 save` и проверяет, что
`http://localhost:4000` отвечает. Лог: `%LOCALAPPDATA%\mixmarkt-crm\autostart.log`.

Почему Планировщик, а не `pm2 startup`: у PM2 нет системной службы на Windows, а демон,
запущенный из обычного терминала, умирает вместе с ним. Задача создаётся от имени текущего
пользователя (без прав администратора) — только так доступны именной канал Docker Desktop.
Если задача не создаётся, скрипт кладёт `.cmd` в папку «Автозагрузка».

## Автодеплой на боевой сервер

Пуш в `main` — и через пару минут на сервере уже новая версия. Выкладка одна и та же для обоих путей
(скрипт `/opt/mixmarkt-crm/bin/apply-release.sh`), поэтому они не конфликтуют.

**Путь 1 — GitHub Actions (основной).** Workflow `.github/workflows/deploy.yml`: GitHub собирает
сервер и клиент, архив едет по SSH на сервер, сервис перезапускается. Нужен один секрет репозитория —
`DEPLOY_SSH_KEY` (приватный ключ `deployer`). Если секрета нет, job `deploy` падает на шаге
«Проверить наличие секрета», но деплой всё равно произойдёт вторым путём.

**Путь 2 — серверный таймер (страховка).** `mixmarkt-autodeploy.timer` каждые 2 минуты запускает
`/opt/mixmarkt-crm/bin/autodeploy.sh`: `git fetch origin/main` → если SHA отличается от
`.deployed-sha`, коммит выкачивается в `/opt/mixmarkt-crm/src`, там собираются сервер и клиент
(`npm ci` только при смене `package-lock.json`), затем вызывается тот же `apply-release.sh`.

- **Сервер** (`37.230.115.170`, `/opt/mixmarkt-crm`): пользователь `deployer` входит только по ключу, а `sudo`
  ему разрешён ровно на один скрипт — `apply-release.sh` (правило в `/etc/sudoers.d/mixmarkt-deploy`).
- **Что делает `apply-release.sh`:** дамп БД в `/var/backups/mixmarkt/pre-deploy-*.dump` → (при изменении
  `package-lock.json`) `npm ci --omit=dev` → подмена `server/dist` и `client/dist/crm` → `systemctl restart mixmarkt-crm`
  → ожидание `/api/health` до 40 с. Если сервис не поднялся — артефакты откатываются на предыдущие, сервис перезапускается.
  Выкладки сериализованы общим lock-файлом `/var/lock/mixmarkt-apply.lock`.
- **Миграции** применяются самим сервисом при старте (`server/src/migrate.ts`), отдельного шага не нужно.
- **Логи и состояние:** `/var/log/mixmarkt-deploy.log` (logrotate), текущий коммит — `/opt/mixmarkt-crm/.deployed-sha`.
  Коммит, на котором упала сборка, пишется в `/opt/mixmarkt-crm/.build-failed-sha` и больше не повторяется
  (сбросить: `rm /opt/mixmarkt-crm/.build-failed-sha`).
- **Ручной запуск:** `systemctl start mixmarkt-autodeploy.service` (сразу проверить `origin/main`),
  кнопка *Run workflow* в GitHub или `sudo /opt/mixmarkt-crm/bin/apply-release.sh /tmp/release-<sha>.tgz`.
- **Ресурсы:** сборка на VPS идёт с `nice 10` и `--max-old-space-size=1024`, на сервере 2 ГБ swap-файла;
  сборка занимает около минуты и не мешает работающему сервису (он перезапускается только на выкладке).

## Архитектура и ключевые решения

- **Единицы измерения.** Всё хранится в *базовых* единицах измерения: масса — г, объём — мл, количество — шт. Накладная/техкарта могут указывать кг, л, десятки — сервер конвертирует по `units.base_factor` и проверяет размерность. UI сам показывает «50 кг» вместо «50000 г».
- **Склад = журнал движений.** Таблица `stock` материализована и обновляется строго внутри транзакций из `movements`; остаток всегда пересчитываем из журнала (см. SQL-рецепт ниже), что даёт аудит и восстановление после сбоев.
- **Себестоимость** — средневзвешенная: обновляется при приходе, списание идёт по текущей средней, партия хранит *снимок* списанного (стабильная история).
- **Раскрытие состава** (`services/expansion.ts`): `сырьё = qty_полуфабриката / (выход% / 100)`, добавки — `qty × расход_на_выход`. Одинаковый код для предпросмотра и для боевого списания — цифры в UI всегда совпадают с фактом.
- **Гонки и отмены.** Строки склада блокируются (`FOR UPDATE` в детерминированном порядке), отрицательные остатки запрещены (флаг `ALLOW_NEGATIVE_STOCK`), отмена партии — обратным приходом по снимку.

### Модель данных
```
units ─┐
       ├─ products ─┬─ stock / movements          (склад и журнал)
       │            ├─ waybill_items -> waybills  (приход)
       ├─ semi_inputs ─ semi_products             (заготовки: role=base + yield_pct | role=additive)
       ├─ tech_card_items ─ tech_cards             (raw|semi ссылка, кол-во на порцию)
       └─ production_batch_items ─ production_batches (отгрузка, снимок списания, статус)
```

## Предложения: как улучшить раздел «Склад»

Уже реализовано: поиск/фильтр по категориям, минимальные остатки с алертом, себестоимость и стоимость склада, полный журнал движений, инвентаризация.

Планы дальнейшего развития:
1. **Учёт мест хранения** — таблица `locations` (цех/камера заморозки/стеллаж) + остаток в разрезе мест; пока места добавляются через `stock` без изменения API-контракта.
2. **Партии и сроки годности** — хранить `batch_no`/`expiry_date` в `movements` прихода, списание по FEFO («что раньше портится — то раньше в дело»), алерт просрочки на панели.
3. **Штрихкоды/QR и маркировка** — поле barcode в `products`, приём накладной сканером, инвентаризация мобильным ТСД.
4. **ABC/XYZ-аналитика** — частота списания сырья из `movements` → приоритет контроля (группа A — точный учёт каждую неделю).
5. **Склад на момент даты** — остаток на любое число: `select sum(qty) from movements where created_at < :date and product_id = …` (журнал уже это позволяет, нужен только график).
6. **Расхождения приёмки** — сравнение «по накладной» vs «по факту» с автоматической корректировкой и отчётом поставщику.
7. **Роли и аудит** — ключевые API-точки уже изолированы транзакциями; далее: JWT + роли (кладовщик/технолог/управляющий) и лог правок.

## Полезные команды

```powershell
# остаток на любую дату (из журнала)
docker exec mixmarkt-crm-db psql -U postgres -d mixmarkt_crm -c "
  select p.name, sum(m.qty) as qty_base
  from movements m join products p on p.id=m.product_id
  where m.created_at < '2026-10-01'
  group by p.name;"

# чистый демо-рестард
docker exec mixmarkt-crm-db psql -U postgres -d mixmarkt_crm -c "drop schema public cascade; create schema public;"
cd server; npm run db:seed
```
